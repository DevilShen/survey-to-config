软件开发全流程决策系统

把散落在项目管理、代码仓库、工单、工时、财务里的过程数据统一起来，回答四个问题：成本为什么超、需求为什么返工、客户到底在抱怨什么、新客户怎么快速配起来。

01

九模块闭环：三条回写链路决定系统是否有效

九个模块不是九个看板，而是一条带反馈的链。任一回写链路断裂，系统就退化为事后统计工具。

实线为主流程，虚线为跨模块回写。L1 决定报价是否会越来越准，L2 决定同一个坑会不会踩第二次，L3 决定版本规划是否由证据驱动。
02

六层架构：语义抽取层为什么必须单列

软件交付的过程数据约 70% 是文本。禁止模型参与就没有输入，放任模型参与就没有可信数字。解法是把模型关进一层：它唯一的写入口是带 schema 的标签表。

禁止跳层：决策服务层不向 Agent 暴露原始明细，也不提供 run_sql。所有进入模型上下文的数据已是带口径的终值。
03

成本偏差五项分解：超支 40% 不是结论

大多数组织把超支归因为「估算不准」，于是投入做更精细的估算模型——但估算偏差通常只占 10%–20%。只盯估算精度，最多解决五分之一的问题。

结论：可改进的不是「报得更准」，而是返工控制（29%）与效率损失来源（25%）。闭合校验失败时，系统不输出占比，只输出缺口清单——不给假精确。
04

需求是一条线，不是一个点

需求状态机（待评审→开发中→完成）无法表达真实情况：同一条需求可能分三次交付，第三次才对。线路图的作用是让「为什么改三次、每次多花多少」变得可查。

关键约束：revision 必须由 PM 工具状态流转自动生成。人工补录只能作冷启动，且单列统计——否则线路图会变成第二次回忆录。
05

「咨询多」是粗信号，必须拆成四类

四类指向完全不同的动作与成本量级。如果 70 条咨询里 60 条是「不会用/找不到」，正确答案是改引导（2 人天），不是重构（200 人天）。

A · 功能存在

不会用

「这个审批怎么发起」「规则怎么设」——功能有，客户不知道怎么做。

指向引导 / 文档 / 培训
成本低（约 1–3 人天）
动作加即时引导、改文案、补帮助中心
B · 功能存在

找不到

「哪里能导出」——功能有，入口藏太深或命名不是客户的语言。

指向信息架构
成本低–中（约 2–5 人天）
动作调入口层级、统一命名
C · 功能存在

理解错

「为什么我改这里那边也变了」——客户的心智模型与产品模型不一致。

指向概念模型
成本高（10 人天起）
动作改交互反馈 / 加约束提示，改文案通常无效
D · 功能不存在

确实缺

「能不能按项目核算」——功能没有，属于产品能力缺口。

指向产品能力
成本按需求评估
动作进候选池，走 RICE + 风险修正打分
分母陷阱：必须用「咨询率 = 咨询数 ÷ 使用次数」，而不是咨询数——否则会把用得最多、最成功的模块误判成最失败的模块去重构。
06

SaaS 初始化：AI 理解与呈现，配置由代码确定性推导

同一份问卷重跑两次，配置必须完全一致。做不到这一点，任何「模型生成配置」的方案都不能用于生产——配置错一位就是事故，且往往两周后才暴露。

01

问卷（分支题库）

按套餐/行业走分支，单份 ≤ 40 题，用客户业务语言提问

02

答案体检

完整性 / 交叉冲突 / 数值缺失，一次性列追问清单

03

规则推导

答案 → 组织/角色/权限/流程/字段，规则有 ID 有单测有版本

04

三件套输出

流程图由配置生成 DSL 渲染，与配置永不脱节

① 流程图主干横向、分支纵向；每个节点标来源题号
② 配置清单按系统录入顺序组织，标三态：已确认 / 默认值 / 待确认
③ 待确认清单冲突与缺失项，标明「影响哪个配置」，阻塞项优先
A/B/C 三类的共同点是「功能存在，但客户用不起来」——这决定了改引导还是改模型；只有 D 类是真正的产品缺口。示例冲突：Q18 金额阈值填 5000，但 Q22 审批层级填 1 级 → 审批流节点数不确定，标阻塞。系统不自动补全，也不猜客户意图。
技术不是难点

六层里只有语义抽取层需要一点工程判断，其余是常规数仓与接口工作。

两条组织前提

工时打到任务级并区分返工；变更留痕并写清原因。缺一条，系统只能输出漂亮的废话。

顺序不能反

前提不具备时，正确做法是先做流程改造。先建系统的结果，是花钱做一个更精致的糊涂账。
